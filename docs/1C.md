# Интеграция HOPS с 1С

## Текущее состояние

Интерфейс адаптера и очередь обмена готовы. Реальный HTTP/CommerceML/OData транспорт намеренно не реализован: формат, адреса и правила вашей конфигурации 1С ещё не предоставлены. Переменные `ONE_C_BASE_URL` и `ONE_C_TOKEN` зарезервированы для будущего транспорта и сейчас не используются. Указание URL не включает обмен.

- `ONE_C_MODE=test` — пустые каталоги и статусы, поиск клиента возвращает отсутствие совпадения. Результат задания явно содержит `mode: "test"`. Товары, склады и клиенты не генерируются.
- Экспорт заказа и бонусные операции в test завершаются ошибкой, а не фиктивным подтверждением. Реальная бонусная сумма не изменяется.
- `ONE_C_MODE=live` — явная ошибка `LIVE_ADAPTER_NOT_CONFIGURED` до реализации согласованного транспорта.

## Контракт адаптера

`lib/integration/contracts.ts` описывает `OneCAdapter`. Каждый ответ транспорта имеет тип `unknown` и проходит строгую проверку Zod до записи в БД. Денежные суммы — целые копейки RUB, бонусы — целые единицы программы, остатки — целые единицы товара; даты — ISO 8601 с часовым поясом; внешние идентификаторы — непустые стабильные строки. Обязателен монотонный `updatedAt` со стороны 1С.

| Метод | Назначение |
| --- | --- |
| `fetchCatalog(cursor, signal)` | Товары, цены, склады, физические остатки, поступления; постраничная дельта |
| `fetchOrderStatuses(cursor, signal)` | Внешний ID заказа, состояние и версия события |
| `exportOrder(order, signal)` | Самовывоз, позиции и зафиксированные цены, клиент, склад, статус; подтверждённый внешний ID |
| `findClient(query, signal)` | Точное сопоставление существующего клиента по подтверждённым бизнесом правилам |
| `operateBonus(operation, signal)` | Начисление, списание либо сторнирование; внешний ID и подтверждённый итоговый баланс |

Товары и склады должны поступать раньше зависимых записей либо в той же странице. Неизвестная ссылка отменяет целую страницу. Дубли ID внутри страницы отклоняются. Пропуск товара в дельте не означает удаление: архивирование передаётся явно как `ARCHIVED`. Внешний ID имеет уникальный индекс; коллизия SKU/slug с другим ID требует разбора оператором.

Изображения сейчас принимаются только из `/images/` в соответствии с CSP сайта. Для внешнего медиахранилища нужно отдельно согласовать доверенные домены, загрузку и политику CSP; произвольные внешние URL отклоняются.

Текущий контракт бонусов подготавливает проводки, но бизнес-правила начисления и списания должен подтвердить владелец 1С. Сайт не создаёт бонусные проводки за покупки автоматически до этого согласования. Итоговый баланс применяется только из более новой подтверждённой версии.

Поиск клиента сохраняет проверенные контакты в момент постановки задания. Если email или телефон изменились до получения ответа, привязка отклоняется с `CLIENT_CONTACTS_CHANGED`; администратор должен заново проверить контактные данные. Результат поиска не может заменить уже назначенный внешний ID другим.

## Остатки и статусы

`Inventory.quantity` — физическое количество, `reserved` — активные резервы сайта, доступно `quantity - reserved`. Импорт меняет количество и исходную версию; резерв сохраняется. Остаток ниже действующих резервов вызывает `STOCK_BELOW_RESERVED`: страница и её курсор откатываются. Оператор должен согласовать отмену/исполнение резервов и повторить обмен. Старые и повторные версии игнорируются отдельно для карточки, цены, остатка, склада, поступления и статуса.

Перед подключением необходимо согласовать момент физического списания, передачу резервов сайта и порядок получения остатков/исполненных заказов. Переходы заказа используют общую серверную функцию `transitionOrder`; пропущенные опросом промежуточные стадии применяются последовательно, обратный переход отклоняется. Если при получении `COMPLETED` уже есть физический снимок с версией не старше исполнения, обмен останавливается с `COMPLETION_STOCK_RECONCILIATION_REQUIRED`, предотвращая двойное списание. Адаптер обязан выдавать согласованную последовательность событий, а не независимые несогласованные снимки. Также нужны гарантии, что снимок после локального исполнения не вернёт в продажу уже выданный товар. Если 1С сообщает только свободные остатки, этот контракт физического количества нужно изменить до включения live.

## Очередь и надёжность

`SyncJob` хранит тип, уникальный `dedupeKey`, данные, попытки, время следующего запуска, lease и результат. `SyncLog` хранит только фиксированные коды: персональные данные, токены, сырые ответы и тексты исключений не записываются. Снимок исходящего заказа находится в защищённой БД в payload задания, в журнал он не попадает.

Работник запускается `npm run sync:worker` или сервисом `worker` в Docker Compose. Админка только создаёт задания и запрашивает повтор; сетевого обмена в HTTP-запросе нет. `processNextJob()` атомарно захватывает запись через `FOR UPDATE SKIP LOCKED`. Lease — 120 секунд, запрос адаптера — не более 30 секунд, транзакция страницы — не более 60 секунд. После сбоя lease освобождается следующим работником; уникальный токен не позволяет старому процессу записать результат за новый.

Каждая страница импортируется с курсором в одной транзакции SERIALIZABLE. Курсоры разделены для test/live и для каталога/статусов. Указатель меняется только после успешной записи всех объектов страницы. Максимум 100 страниц за попытку; продолжение подхватывает сохранённый курсор. Повторные страницы безопасны благодаря ID и версиям. До 5 автоматических попыток с задержкой 15/30/60/120 секунд; после исчерпания или постоянной ошибки — `FAILED`, доступен ручной повтор.

Задание заказа — уведомление об изменении: перед первым запросом работник фиксирует текущее состояние заказа, поэтому несколько ещё не отправленных уведомлений могут объединиться в одно актуальное состояние. Снимок сохраняется до запроса и повторно отправляется неизменным с тем же ключом. Параллельные работники сериализуют экспорт одного заказа; если статус уже изменился, повтор старого снимка помечается `superseded`, а актуальное состояние ставится в очередь. Уже подтверждённая версия повторно не отправляется.

В 1С необходимо обеспечить уникальность локального `localId`, идемпотентность каждой операции по `idempotencyKey`, возврат того же результата после таймаута и отказ от более старых `updatedAt`. Разные статусы одного заказа могут иметь разные ключи; это не должно создавать новые заказы. Эти гарантии обязательны на стороне принимающего API: сама очередь не может обеспечить exactly-once через сеть, в частности при задержанном ответе после истечения lease. Бонусная операция также должна повторяться с тем же ключом; локальный баланс присваивается из подтверждённого ответа, а не повторно увеличивается.

## Что нужно получить от специалиста 1С

1. Конфигурацию и версию 1С, тестовый контур, протокол, схему аутентификации, описание endpoints/форматов и лимитов.
2. Реальные обезличенные примеры товаров, цен, складов, остатков, поступлений, клиентов и всех статусов заказа; правила маркировки/категорий и единиц измерения.
3. Гарантии ID, версий, порядка событий и постраничных курсоров, правила удаления и полного восстановления после утраты курсора.
4. Маппинг статусов, правила резервирования и списания, идемпотентность создания/обновления заказов и бонусных проводок.
5. Подтверждённые правила поиска клиента и бонусов; телефон/email без проверки владения не должны автоматически открывать доступ к чужим бонусам.

После получения контракта: реализовать транспорт, ограничить HTTPS-адреса доверенным сервером, передавать `AbortSignal`, добавить проверку ответов и контрактные тесты на реальных обезличенных образцах, проверить сбой после внешнего подтверждения, повторы и параллельные работники. Только затем включить `live`. Секреты хранятся только в окружении сервера.
