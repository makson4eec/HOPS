# Каталог из 1С

Используется существующая PostgreSQL/Prisma и таблица `Product`. Новых зависимостей нет. Серверные файлы находятся в `lib/1c/` (в проекте нет `src/`).

## Один раз перед запуском

Скопировать `.env.example` в `.env`, заполнить существующий `DATABASE_URL`, затем:

```sh
npm run db:generate
npm run db:migrate
npm run db:seed
```

Миграция добавляет поля без удаления данных. Существующие `externalId` (уникальный), `imageUrl`, `updatedAt` сохранены: это аналоги `external_id`, `image_url`, `updated_at`. Новые `categoryId` и `isActive` соответствуют SQL `category_id` и `is_active`. Старым товарам сохраняется источник `manual`; один внешний ID не делает их собственностью импорта.

## Проверка без 1С

В `.env`:

```dotenv
ONE_C_USE_MOCK=true
ONE_C_ALLOWED_CATEGORY_IDS=mock-beer,mock-lemonade
ONE_C_ALLOWED_PRODUCT_IDS=mock-103
ONE_C_SYNC_SECRET=ЗАМЕНИТЬ_НА_СЛУЧАЙНЫЙ_СЕКРЕТ
```

Секрет можно сгенерировать: `node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"`. Запустить `npm run dev` и вызвать POST ниже. Ожидается `received: 4, allowed: 3, created: 3, updated: 0, disabled: 0, errors: []`; повторный запуск даст `created: 0, updated: 3`. В `/catalog` будут три тестовых товара, два без остатка. Mock использует тот же импорт и пишет в указанную БД; проверяйте его на тестовой базе.

## Как подключить реальную 1С

В серверном `.env` (или переменных окружения хостинга):

1. `ONE_C_API_URL=https://...` — GET, **полный снимок** каталога JSON.
2. `ONE_C_API_KEY=...` — Bearer; либо `ONE_C_LOGIN=...` и `ONE_C_PASSWORD=...` для Basic. Если заполнены оба способа, используется Bearer; все пустые — без авторизации.
3. `ONE_C_ALLOWED_CATEGORY_IDS=12,15,27`.
4. `ONE_C_ALLOWED_PRODUCT_IDS=123,456` — необязательно, дополнительные разрешённые товары.
5. `ONE_C_USE_MOCK=false`, заполнить `ONE_C_SYNC_SECRET` случайным значением.
6. При отличии JSON изменить блок `fields` / `extractOneCProducts` в `lib/1c/normalize.ts`. При необходимости сопоставить ID категорий существующим разделам сайта в `websiteCategories` там же; без сопоставления товары доступны в «Все товары». Фильтрация разрешений всегда по исходным ID.
7. Перезапустить сервер (при изменении кода — пересобрать), вызвать `POST /api/1c/sync`.

```sh
# HOPS_URL и ONE_C_SYNC_SECRET заданы в окружении вызывающего процесса.
curl --fail-with-body --max-time 90 -X POST "$HOPS_URL/api/1c/sync" \
  -H "Authorization: Bearer $ONE_C_SYNC_SECRET"
```

`GET /api/1c/sync` возвращает только флаги настройки URL, БД/миграции, магазина, режима и готовности; 200 — готово, 503 — настройка не завершена. 1С при health-check не вызывается. POST без правильного секрета — 401, одновременный запуск — 409, ошибка выгрузки — 502, БД/настройки — 503. Статистика ошибок содержит безопасные коды; счётчики записей при откате равны нулю.

## Формат и поведение

- Примеры полей — `lib/1c/mock.json`. Поддерживаются массив, `{ products: [...] }`, `{ items: [...] }`, `{ value: [...] }`. До 5000 товаров / 10 МБ / 20 секунд на HTTP. Пагинация, дельты, вложенные остатки требуют адаптации этого блока под полный снимок; обнаруженная незавершённая страница отклоняется.
- Цена на входе — рубли, в существующей БД — копейки; остаток — целые физические единицы до резервов сайта. Отрицательный остаток становится 0. Отсутствующие обязательные поля, повтор ID и некорректный JSON откатывают весь импорт, включая деактивацию.
- Разрешение: категория **ИЛИ** товар. Два пустых списка разрешают 0 товаров. Успешный пустой снимок или пустой результат фильтра **деактивирует все товары `source="1c"`**. Исчезнувшие товары не удаляются; вернувшиеся активируются. Ручные товары не изменяются, конфликт их внешнего ID откатывает импорт.
- Новые товары публикуются. У существующих сохраняются URL, редакционный статус и признак новинки. Каталог, карточка, ассортимент, sitemap и оформление учитывают `is_active`. Страницы читают только БД.
- Остатки привязаны к существующему магазину `hops-store` из seed. `Product.stock` хранит последний физический снимок 1С, а самовывоз учитывает резервы через `Inventory`. При остатке ниже резервов сохраняются резервы и 0 свободных единиц. Реальный API должен согласовать физический остаток с выданными заказами; многоскладской обмен остаётся в существующем адаптере.
- Изображения: локальные `/images/...` или публичные HTTPS URL без авторизации. API и его credentials вызываются только сервером; картинки не должны требовать пароль 1С.
- Старые `ONE_C_MODE`, `ONE_C_BASE_URL`, `ONE_C_TOKEN`, кнопка обмена в админке и очередь `lib/integration` относятся к прежнему обмену заказами/клиентами/бонусами. Новый импорт каталога запускается через этот endpoint, независимо от них.

## Cron каждые 5 минут

Планировщик любого сервера может вызывать endpoint. Создать файл `/etc/hops/1c-cron.env`, доступный только пользователю cron, с `HOPS_URL=https://ваш-сайт` и `ONE_C_SYNC_SECRET='ваш-секрет'`. Не коммитить его. Пример crontab:

```cron
*/5 * * * * . /etc/hops/1c-cron.env && curl --silent --show-error --fail-with-body --max-time 90 -X POST "$HOPS_URL/api/1c/sync" -H "Authorization: Bearer $ONE_C_SYNC_SECRET" >> /var/log/hops-1c-sync.log 2>&1
```

Проверки: `npm run typecheck`, `npm run build`, `npm test`. Для тестов реальной PostgreSQL задать `TEST_DATABASE_URL` на отдельную БД **hops_test**: новый тест использует собственную временную схему.
